# 0. Introduction

## 0.1 Purpose & Scope

This TDD specifies **how** the FitVibe system will implement the features and constraints defined in the [PRD](../1.Product_Requirements/1.Product_Requirements_Document.md) (WHAT/WHY) and satisfy the [QA Plan](docs/4.Testing_and_Quality_Assurance_Plan/4a.Testing_and_Quality_Assurance_Plan.md) (HOW WELL).

## 0.2 Audience & Reading Guide

- **Engineers** implement according to specs, contracts, and runbooks.
- **QA** uses RTM links to derive tests and quality gates.
- **Security/Compliance** verifies controls, data classification, GDPR flows.
- **Product/Design** confirms that behavior matches PRD intent.

## 0.3 Assumptions & Constraints

- Monorepo with **pnpm** workspaces; Node.js 20 LTS; React 18; PostgreSQL = 14 (target 16-18 locally).
- All external calls (email) are **adapterized** and mockable for tests.
- Privacy-by-design: **private-by-default** content, explicit consent for public sharing.
- Deployments run behind **TLS** with reverse proxy (NGINX) and **Let's Encrypt** certificates.

## 0.4 Versioning & Changelog

- **Change policy:** Any change to interfaces, schema, or security controls must update TDD and the related ADR, and link into QA RTM.

# 6. Data Design

This section defines the **logical schema**, **entity dictionary**, **indexing strategy**, **partitioning/archival**, **retention & classification**, and the **migrations plan**.

This chapter describes the **current** FitVibe schema after the 2026-08-31 baseline rebuild:

- lookup tables (`roles`, `genders`, `fitness_levels`, `exercise_types`) instead of `code_sets` / `code_values`;
- handle on `profiles.alias` (not `users.username`);
- logged work in `exercise_sets`; planned targets in `planned_exercise_attributes`;
- field diffs in `user_state_history`; security/GDPR events in `audit_log`;
- append-only `cookie_consents`; hashed `user_tombstones`.

> Conventions: snake_case identifiers; UTC `timestamptz`; UUID primary keys; privacy-by-default (`profiles.visibility` and `sessions.visibility` default `private`; exercises default not public).

## 6.1 Architectural Overview

The model is organized into six layers:

1. **Identity & security** — `users`, `roles`, `profiles` (required `alias` + `alias_changed_at`), `user_contacts`, `auth_sessions`, `refresh_tokens`, `auth_tokens`, 2FA (`user_2fa_settings`, `backup_codes`, `pending_2fa_sessions`), brute-force tables.
2. **Catalog & i18n** — `exercises` (personal + global, default private), `translations` (seeded from locale JSON).
3. **Planning & logging** — `plans`, `sessions` (simple UUID PK), `session_exercises`, `exercise_sets`, `planned_exercise_attributes`.
4. **Progress** — `personal_records` (current PR per exercise/metric), `bio_*` / `perf_*` attributes and values, `session_summary` / `weekly_aggregates`.
5. **Social & gamification** — followers, feed (items/likes/comments/bookmarks/blocks/reports), points, badges, six-vibe levels and change trail, `mv_leaderboard` (exposes `profiles.alias`).
6. **Ops & GDPR** — `audit_log` (append-only; `actor_user_id` ON DELETE SET NULL), `user_state_history` (delete with user), `cookie_consents` (append-only), hashed `user_tombstones`, `idempotency_keys`, `blacklist`, `contact_messages`.

**Keys & types:** entity IDs are `uuid`; timestamps are `timestamptz` (UTC).
**Handle vs display name:** `profiles.alias` is the unique login/handle; `users.display_name` is the shown name (FR-009).

## 6.3 Core Entities (day-to-day)

Below are the **interfaces teams build against**. Detailed columns are in the ERD.

### 6.3.1 Identity & security

- **users** — account; no `username`; units, default session visibility, privacy flags (`allow_followers`, `show_email`, `show_weight`, `show_fitness_level`), terms/privacy versions, `deleted_at` / purge timestamps.
- **profiles** — 1:1; required unique `alias` (citext) + `alias_changed_at`; fitness_level + training_frequency on the row; visibility default `private`.
- **user_contacts** — email/phone; unique primary email.
- **auth_sessions / refresh_tokens / auth_tokens** — one token stack (no extra verification/reset tables).
- **user_2fa_settings + backup_codes + pending_2fa_sessions** — the only 2FA stack.

### 6.3.2 Catalog & i18n

- **exercises** — `owner_id` null = global; default `is_public = false`; single `description` column; `tags` jsonb.
- **translations** — namespace/key/language; partial unique on active rows. Catalog and UI strings are **seeded**, not migrated.

### 6.3.3 Planning & logging

- **plans** — `user_id` owner.
- **sessions** — simple UUID PK; visibility default `private`.
- **session_exercises** — ordered; `exercise_name` snapshot.
- **exercise_sets** — logged work (source of truth for actuals).
- **planned_exercise_attributes** — one row per session exercise for targets. There is no `actual_exercise_attributes` table.

### 6.3.4 Progress

- **personal_records** — slim current PR (`metric`, `value`, `achieved_at`, `is_current`).
- **bio_attributes / bio_attribute_values / bio_attribute_selections** and the **perf\_\*** pair — measurements. Catalogs are seeded.

### 6.3.5 Social & gamification

- **followers**, **feed_items** (session-backed; no unused score/kind/target\_\*), likes, comments, bookmarks, blocks, reports.
- **user_points**, **badge_catalog**, **badges**, **user_domain_vibe_levels**, **vibe_level_changes**, **mv_leaderboard**.

### 6.3.6 Ops & GDPR

- **audit_log** — security and GDPR events; keep rows on DSR, null the actor.
- **user_state_history** — field diffs (alias, visibility, units, fitness_level, …); delete with user; includes `actor_user_id` + `request_id`.
- **cookie_consents** — append-only; nullable `user_id`; hashed `client_key`; no unique-on-IP overwrite.
- **user_tombstones** — hashes of email and alias after purge.

#### 6.2.1.4 profiles

**Design Note:** The profile data is normalized across three tables for better performance and data integrity:

- **profiles** - Static profile data (immutable fields, preferences)
- **user_contacts** - Contact information (email, phone) with verification status
- **user_metrics** - Time-series metrics (weight, fitness_level over time)

This normalized design provides:

- Better query performance (can query contacts/metrics independently)
- Proper normalization (users can have multiple contacts)
- Time-series separation (metrics vs static data)
- Reduced table size for hot-path queries

| Column           | Type        | Constraints / Notes                                                        |
| ---------------- | ----------- | -------------------------------------------------------------------------- |
| user_id          | uuid        | **pk**, **fk ? users.id (ON DELETE CASCADE)**, **unique** (1:1)            |
| alias            | citext      | **unique**, nullable; public profile identifier                            |
| avatar_asset_id  | uuid        | **fk ? media_assets.id** (nullable, ON DELETE SET NULL)                    |
| bio              | text        | 0-500 chars (CHECK constraint)                                             |
| date_of_birth    | date        | **immutable after first non-null set**                                     |
| gender_code      | text        | **fk ? genders.code** (ON DELETE SET NULL) (**immutable after first set**) |
| visibility       | text        | **CHECK** IN ('private', 'link', 'public'); default 'private'              |
| timezone         | text        | e.g., `Europe/Berlin`                                                      |
| unit_preferences | jsonb       | default `{}`; e.g., `{"weight":"kg","distance":"km"}`                      |
| created_at       | timestamptz | default `now()`                                                            |
| updated_at       | timestamptz | default `now()`                                                            |

**Indexes:** `idx_profiles_alias` on `alias` WHERE `alias IS NOT NULL`, `idx_profiles_visibility` on `visibility` WHERE `visibility = 'public'`.

**Related Tables:**

- **user_contacts** - Email, phone, verification status (see 6.2.1.5)
- **user_metrics** - Time-series weight, fitness_level, training_frequency (see 6.2.1.6)

### 6.3.5 Progress & Recovery

#### 6.3.5.1 personal_records

**Design Note:** Uses ENUM for `pr_type` instead of text `metric` for:

- Better performance (ENUM is more efficient than text)
- Database-level constraint enforcement
- Type safety in application code
- Clearer domain model

| Column       | Type          | Constraints / Notes                                                                          |
| ------------ | ------------- | -------------------------------------------------------------------------------------------- |
| id           | uuid          | **pk**                                                                                       |
| user_id      | uuid          | **fk ? users.id**                                                                            |
| exercise_id  | uuid          | **fk ? exercises.id**                                                                        |
| pr_type      | enum          | **ENUM** ('1rm', 'volume', 'reps', 'duration'); not null                                     |
| value        | numeric(10,2) | not null                                                                                     |
| reps         | integer       | nullable; for 1RM calculation context                                                        |
| weight_kg    | numeric(10,2) | nullable; weight used for the PR                                                             |
| duration_sec | integer       | nullable; duration for time-based exercises                                                  |
| session_id   | uuid          | nullable; FK to sessions(id) - enforced at application level per ADR-005                     |
| set_id       | uuid          | nullable; reference to specific set (no FK for manual entry flexibility)                     |
| achieved_at  | timestamptz   | not null; default `now()`                                                                    |
| is_current   | boolean       | default `true`; partial **unique** `(user_id, exercise_id, pr_type) WHERE is_current = true` |

## 6.4 Extensibility Layer

### 6.4.1 Enumerations ? `code_sets` / `code_values`

All former enums (status, visibility, difficulty, set types, etc.) are **data-driven**:

- `code_sets(key)` ? set (e.g., `session_status`, `visibility`, `muscle_group`).
- `code_values(set_id, code, label)` ? values within a set.
- Domain tables reference **`code_values.id`** (e.g., `sessions.status_id`).

**Benefits:** runtime additions, localization via `code_value_i18n`, central governance, consistent analytics.

### 6.4.2 Attributes (typed EAV) ? `attributes` / `attribute_values`

Fast expansion for metrics without migrations:

- `attributes` defines a key, label, type (`int|numeric|text|boolean|date|timestamptz|jsonb|code_value`), optional unit set.
- `attribute_scopes` restricts valid entity types (e.g., `body_measurement`, `recovery_log`, `exercise_set`).
- `attribute_values` stores **exactly one** of the typed value columns per row (enforced by a CHECK).
- Units and coded values link to **`code_values`**.

**Recommended use:**

- Keep **hot fields** in base tables (e.g., `weight_kg`, `rpe`).
- Put **expanding/long-tail** metrics in attributes (e.g., HRV, circumference variants, readiness scores).

## 6.5 Internationalization

- `translation_fields(entity_type, field_key)` is the **allow-list** to prevent junk keys.
- `translations` stores localized text per field (unique on `entity_type, entity_id, lang, field_key`).
- `translation_cache` may store pre-rendered or AI-generated translations; not SoT.

## 6.6 Data Integrity & Constraints

**Keys & constraints**

- All IDs `uuid`, timestamps `timestamptz`.
- Composite PKs: `user_roles(user_id, role_id)`, `exercise_tags(exercise_id, tag_id)`, `followers(follower_id, followee_id)`, etc.
- Partial unique: `personal_records(user_id, exercise_id, metric) WHERE is_current=true`.
- Ordering uniques: `session_exercises(session_id, order_index)` and `exercise_sets(session_exercise_id, order_index)`.

**ON DELETE policies (high-level)**

- **CASCADE** for dependent private data: `profiles`, `user_sessions`, `followers`, `likes`, `bookmarks`, `badges`, etc.
- **SET NULL** where history should persist detached: `verification_tokens.user_id`, `reset_tokens.user_id`, `share_links` targets.
- **No cascade** for historical facts that must remain unless specifically noted.

**Critical CHECKs**

- `followers`: `follower_id != followee_id`.
- `share_links`: exactly one of (`feed_item_id`, `session_id`) is set.
- `exercise_sets.rpe`: 1..10.
- **Session lifecycle** (application/DB):
  - `planned`: `started_at IS NULL AND completed_at IS NULL`
  - `in_progress`: `started_at IS NOT NULL AND completed_at IS NULL`
  - `completed`: `started_at IS NOT NULL AND completed_at IS NOT NULL`

## 6.7 Indexing & Partitioning

**Hot-path indices**

- Sessions: `(owner_id, status, planned_at DESC)` and partial `WHERE deleted_at IS NULL`.
- Feed: `(visibility_id, published_at DESC)` and public partial index.
- PRs: partial `WHERE is_current=true` on `(user_id, exercise_id, metric)`.
- Notifications: `(user_id, created_at DESC) WHERE is_read=false AND (expires_at IS NULL OR expires_at>now())`.
- Translations: `(lang, entity_type, entity_id)`.
- Attributes: `(entity_type, entity_id, attribute_id, measured_at DESC)`.

**Partitioning**

- **sessions**: monthly range partitions on `planned_at` (or `started_at` if present). Keep a **default** partition. Archive or detach partitions = 24 months old.
- **audit_log**, **user_points**: consider monthly partitions at scale; else retain single table + time-based retention and vacuum tuning.
- Optional: cold partitions on cheaper storage; keep query router aware of active windows.

## 6.8 Soft-Delete, Archival & Retention

- **Soft delete**: `users.deleted_at`, `feed_items.deleted_at`, `sessions.deleted_at`.
- **Archive**: `exercises.archived_at`, `plans.archived_at`.
- **GDPR / DSR** (NFR-002): export <=24h, hard delete <=30d, backup purge <=14d, consent opt-out <=5m. Privacy-by-default.

## 6.13 Data Quality & Integrity Rules

- **Referential integrity**: FKs with explicit `ON DELETE` (cascade for session children; set-null where audit needs to persist).
- **Enumerations via FKs**: prefer `code_values` over CHECKs for domain lists. Use CHECKs for invariants (e.g., `rpe BETWEEN 1 AND 10`, session lifecycle timestamps, `share_links` XOR FK rule).
- **Soft-delete discipline**: all queries include `deleted_at IS NULL` where applicable; define partial indexes for hot paths.
- **Text search**: `pg_trgm` for fuzzy name search; consider tsvector if we expand full-text.
- **Caching/derived**: keep `mv_leaderboard`, leaderboard caches, and translation cache rebuildable; document refresh cadence.
- **Transactions**: nested session writes are atomic; idempotency enforced via `(user_id, source, source_id)` in `user_points`.
